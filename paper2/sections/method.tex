\section{Methodology}
\label{sec:method}

\textbf{Testbed.} We use ResultBench~\cite{pathak2026surviving} unchanged
except for the mechanisms above: the database-backed portal A behind the
waiting room, the same two-CPU budget, the same synthetic dataset of
\num{200000} students and the same correctness oracle. The scenario is the
first paper's compressed surge (20\,s before release, a peak at release that
decays over 30\,s, arrivals for 90\,s) with 240\,s more for queues to empty.
Load is a multiple of A's calibrated capacity. Each configuration is run
three times; we report medians with 95\% bootstrap intervals.

\textbf{Students.} The load generator is open loop. Each student waits for a
response up to a patience drawn from 5--20\,s, retries after a failure with
probability 0.8 (0.9 after running out of patience), presses refresh while
queued about once a minute and, new in this paper, gives up after a
\emph{queue patience}. With a wait estimate, a student whose time already
waited plus the estimate exceeds their queue patience leaves at once
(\texttt{users.eta\_balk}). \todo{Replace or bracket these values with the
behaviour-study measurements.}

\textbf{Bots.} Scrapers start at release and walk through \num{1000}
consecutive roll numbers each, polling every 0.5\,s and never giving up; they
keep one session or start a new one for every request. Bot requests count in
the portal's load but in no student metric.
